Documentación de cambios y puesta en marcha del entorno local
Backend: MelinaCora/DesPescar, rama features/full-integration-docker-setup · Frontend: TenSF25/DesPescar, rama features/merge-koi-gateway · 4 de octubre de 2026

Cómo usar este documento. Es el registro de los cambios hechos al poner en marcha el entorno local y del estado en que quedó; no es una guía de uso. Para levantar el entorno usá la documentación por servicio: empezá por docs/README.md (índice, requisitos, orden de arranque y equivalencias entre Linux y Windows) y seguí con la guía de cada servicio. Algunas partes de este registro se actualizaron al publicarlo: el Docker vive en database/ y la contraseña de MySQL pasó a ser común.

1. Resumen

Se dejó funcionando el entorno local completo: base de datos MySQL en Docker, siete microservicios Spring Boot y el gateway, con datos de ejemplo y usuarios de prueba. Además se corrigieron dos problemas de comportamiento:

  • El buscador de vuelos exigía iniciar sesión. Ahora la consulta de vuelos es pública y solo se pide login al avanzar con la compra.
  • La redirección al login al seleccionar un vuelo fallaba y, tras iniciar sesión, no devolvía al usuario al vuelo elegido.
Alcance de la verificación. Los endpoints se probaron con curl contra el gateway. De los cambios en el frontend, el usuario confirmó que la redirección al login funciona. Que, tras iniciar sesión, se vuelva a /booking/baggage con el vuelo elegido no fue confirmado en el navegador.

2. Base de datos (MySQL en Docker)

Los servicios esperan MySQL en localhost:3306 con usuario root. En el repositorio, la carpeta database/ contiene todo lo necesario:

ArchivoFunción
database/docker-compose.ymlMySQL 8 como despescar-mysql (puerto 3306, volumen mysql_data, healthcheck por TCP) y Adminer en el puerto 8090.
database/init/01_create_databases.sqlCrea las 7 bases de datos la primera vez que arranca el contenedor.
database/.env.examplePlantilla de DB_PASSWORD. Normalmente no hace falta crear un .env.
database/seed/Script para cargar datos de ejemplo (sección 4).
database/README.mdGuía de conceptos e instalación de Docker (autoría de Noelia, actualizada).

Bases de datos: despescar_identity, despescar_hotel, despescar_flight, despescar_package, despescar_reservation, despescar_payment y despescar_koiia. Todos los servicios usan ddl-auto=update, por lo que Hibernate crea las tablas al arrancar.

Contraseña común de MySQL

Antes cada persona escribía su propia contraseña en los siete application.properties, lo que producía conflictos constantes y dejaba contraseñas publicadas. Ahora los siete leen spring.datasource.password=${DB_PASSWORD:despescar_dev} y el compose usa el mismo valor por defecto, despescar_dev. Nadie tiene que tocar archivos. Los tests usan H2 en memoria y no se modificaron.

Atención. Quien ya tenga un volumen de MySQL creado con otra contraseña debe recrearlo (docker compose down -v), porque MySQL solo toma la contraseña al crear el volumen. Las contraseñas anteriores siguen en el historial de otras ramas del repositorio público; si se reutilizan en otro lado conviene cambiarlas.

Puerto de Adminer

El Adminer original usaba el puerto 8080, el mismo que identity-service, y provocaba el error Port 8080 was already in use. Ahora está en http://localhost:8090 (servidor mysql, usuario root).

Cómo arrancar cada servicio

Cada servicio va en su propia terminal. Se usó mvn (Maven 3.8.7 instalado), porque los mvnw no tienen permiso de ejecución y koi-ia-service y gateway-service no traen mvnw.

export JWT_SECRET='despescar-dev-secret-key-2026-must-be-long-enough'
cd services/identity-service
mvn spring-boot:run

Variables de entorno que usa el proyecto:

VariableQuién la necesitaObligatoria
JWT_SECRETidentity, flight, reservation, package, payment, gatewaySí, la misma en todos. Se usó una clave de ejemplo solo para desarrollo.
RESERVATION_SERVICE_SYNC_TOKENreservation-service y payment-serviceImprescindible para pagar, el mismo valor en los dos (ver 6.1). Si queda vacía los servicios arrancan, pero crear un pago falla con un error 502 ("Reservation-Service rechazo la consulta de la reserva").
GROQ_API_KEYkoi-ia-serviceSí para que responda la IA. Se arrancó con una clave de relleno.
MERCADOPAGO_*payment-serviceNo para arrancar (valor vacío por defecto). MERCADOPAGO_ACCESS_TOKEN con una credencial de prueba es necesaria para generar el enlace de pago.

koi-ia-service debe arrancarse así, porque su código de pruebas no compila:

mvn -Dmaven.test.skip=true spring-boot:run

El archivo KoiAiAssistantTest.java usa OllamaClient y un método extractTravelInfo que ya no coinciden con el código actual (ahora usa Groq). No se modificó.

Límite de espera del gateway

El gateway corta cualquier petición a los 5 segundos con un error 504. Con el equipo sin memoria libre, el registro de usuarios tardaba más: el usuario se creaba en el backend pero el frontend recibía un error. Para esta ejecución se subió el límite a 30 segundos mediante un argumento de arranque, sin modificar el application.yml:

cd services/gateway-service
mvn spring-boot:run \
  -Dspring-boot.run.arguments="--resilience4j.timelimiter.instances.gatewayCircuitBreaker.timeoutDuration=30s \
  --spring.cloud.gateway.httpclient.response-timeout=30s"

Se suben los dos límites (el del circuit breaker y el de respuesta del cliente HTTP). Probado con un servidor de prueba que tarda 8 segundos: pasa por el gateway con 200; con el límite de 5 segundos cortaba con 504. Es necesario para el chatbot, que puede tardar hasta unos 10 segundos. Guías: docs/gateway-service.md y docs/koi-ia-service.md.

6. Cambios en el código

6.1 Backend: consulta pública de vuelos (gateway)

Problema. El gateway exigía token Bearer en todo /api/, incluso para listar aeropuertos o buscar vuelos, por lo que el buscador aparecía vacío sin sesión. Además flightservice ya declaraba esas rutas como públicas, de modo que el bloqueo estaba solo en el gateway.

Cambio. Archivo services/gateway-service/.../filter/GatewayJwtAuthFilter.java: se agregó el método isPublicFlightRead y se invoca junto a isPublicPath. Deja pasar sin token únicamente peticiones GET a:

  • /api/flights, /api/flights/search y /api/flights/{id}
  • /api/airports y /api/airports/code/{code}
  • /api/fares

Verificado con curl, sin token: aeropuertos, vuelos y búsqueda devuelven 200. Siguen protegidos: POST a /api/airports (401), /api/airlines (401), /api/packages (401), /api/users (401) y /hoteles (403, lo responde el propio hotel-service).

La búsqueda exige los parámetros origin, destination, departureDate y passengers; returnDate es opcional.

Rutas internas bloqueadas. En esta rama el gateway además responde 403 a todo /api/bookings/internal/**. Son las rutas con las que payment-service consulta y confirma reservas (usan el encabezado X-Internal-Service-Token, con el valor de RESERVATION_SERVICE_SYNC_TOKEN). Antes solo las protegía ese token, y el gateway no las filtraba: un usuario con sesión podía llegar a ellas. Los servicios se hablan directo por su puerto, así que el flujo de pago no se ve afectado. Probado con el gateway levantado: las rutas internas dan 403 (con y sin token), mientras /api/bookings/1, /api/payments y /api/users siguen dando 401 sin sesión.

6.2 Frontend: redirección al login y retorno al flujo de compra

Problema. ProtectedRoute guardaba el location global del navegador, que no se puede almacenar en el historial, y la navegación a /login fallaba. Además, al iniciar sesión se enviaba siempre al inicio del rol, ignorando la página que el usuario intentaba abrir. PublicRoute, que envuelve /login, también redirigía al inicio apenas el usuario quedaba autenticado.

Archivo (en src/)Cambio
components/Routes/ProtectedRoute.tsxUsa useLocation() de React Router y guarda esa ubicación como state.from.
features/auth/postLoginPath.ts (nuevo)Función getPostLoginPath: devuelve la ruta guardada en state.from (solo si empieza con /) o, si no hay, el inicio del rol.
features/auth/hooks/useAuth.tsEl login navega al destino calculado con getPostLoginPath, con replace: true.
components/Routes/PublicRoute.tsxUsa el mismo destino, para no competir con la redirección del login.

Se comprobó que el proyecto compila (tsc --noEmit) y pasa el linter en las carpetas modificadas.

6.3 Base de la rama y compatibilidad con el frontend

La rama parte de features/auditoria-y-chatbot, no de features/payment-service-update. Esta última agrega un commit (7d5fab00, Checkout API con pago grupal por fracciones) que reemplaza POST /api/payments por /api/v1/payments, lo deja sin autenticación (permitAll) y no está enrutado en el gateway. El frontend features/merge-koi-gateway paga con POST /api/payments y no tiene pantalla ni código para el pago grupal en ninguna de sus 21 ramas, por lo que ese commit queda fuera hasta que el equipo defina el contrato.

Límite de la verificación: es lectura de código; el flujo completo no se probó en ejecución. El pago además requiere una credencial de prueba de MercadoPago. Los cambios de asientos que el frontend tiene sin commitear no se revisaron.

Flujo de selección de vuelo

  1. Búsqueda en /vuelos (pública).
  2. Al elegir vuelo: si la búsqueda es de ida y vuelta, el primer clic elige la ida y el segundo la vuelta; con solo ida, el primer clic basta.
  3. Se navega a /booking/baggage (ruta protegida): sin sesión se redirige a /login y, tras iniciar sesión, se vuelve a esa misma dirección.
  4. Elección de tarifa y equipaje, luego /booking/seats (asientos) y /booking/checkout.

Los dos clics en una búsqueda de ida y vuelta son el comportamiento original del proyecto, no un fallo.

8. Pendientes y recomendaciones

  • Memoria: el equipo tiene 6,9 GB de RAM y el swap llegó a estar lleno (5,4 de 5,5 GB). Conviene cerrar IntelliJ y detener koi-ia-service si no se usa. Cerrar IntelliJ no afecta a los servicios, que no dependen de él.
  • Chatbot: koi-ia-service necesita una GROQ_API_KEY real (https://console.groq.com/home). Sin ella no responde con IA. Además, por el código, no puede traer hoteles ni paquetes: sus herramientas llaman a hotel-service y package-service sin token y esos servicios exigen sesión (comprobado: hotel-service responde 403 sin token y 200 con token). Y su búsqueda de vuelos ignora las fechas (trae los tres primeros vuelos de esa ruta).
  • Windows: las guías incluyen los comandos para PowerShell, revisados uno por uno pero no ejecutados en Windows. Hay que validarlos con una persona que use Windows. También se agregó un .gitattributes para que seed.sh conserve sus saltos de línea de Linux al clonar en Windows.
  • payment-service (puerto 8084) no se arrancó. Los datos de MercadoPago quedarían vacíos, por lo que los pagos no funcionarían de verdad.
  • Checkout API / pago grupal: sigue en la rama features/payment-service-update. Antes de integrarlo hay que acordar con su autora o autor si se mantiene POST /api/payments, cómo se enruta en el gateway y cómo se autentica, y que el frontend tenga una pantalla para usarlo.
  • Contraseñas en el repositorio: resuelto para MySQL en esta rama (variable DB_PASSWORD con valor común). Siguen existiendo contraseñas anteriores en el historial de otras ramas públicas.
  • Variables de entorno: JWT_SECRET y GROQ_API_KEY solo existen en los procesos arrancados; hay que exportarlas de nuevo tras cada reinicio.
  • Docker al iniciar: sudo systemctl enable docker evita tener que arrancarlo a mano.
  • Tests de koi-ia-service: actualizar KoiAiAssistantTest.java al cliente actual.
  • /api/fares no tiene ruta en el gateway (404). No afecta a la búsqueda, porque las tarifas vienen dentro de cada vuelo; haría falta solo para una pantalla de administración de tarifas.
  • Precios: en la búsqueda el vuelo EZE-COR apareció como ARS 15.060 y no 60. No se investigó el motivo de la conversión.
  • Hoteles y paquetes siguen exigiendo sesión. Si deben verse sin iniciar sesión, hay que cambiar el gateway y los SecurityConfig de hotel-service y package-service.
  • Scripts de carga: ya están en database/seed/.

9. Guía rápida para levantar todo

  1. Docker: sudo systemctl start docker
  2. MySQL: cd database && docker compose up -d y esperar a healthy.
  3. Servicios, cada uno en su terminal, con JWT_SECRET exportado (y RESERVATION_SERVICE_SYNC_TOKEN igual en reservas y pagos, GROQ_API_KEY si corresponde): identity-service, flightservice, hotel-service, package-service, reservation-service, payment-service, koi-ia-service (con -Dmaven.test.skip=true) y por último gateway-service.
  4. Datos de ejemplo: ./database/seed/seed.sh
  5. Frontend (features/merge-koi-gateway): pnpm dev en http://localhost:5173, que apunta al gateway en el puerto 8087.

El detalle de cada paso y los problemas comunes están en la guía de cada servicio, a partir de docs/README.md. Arrancar todos los servicios a la vez con poca memoria los hace tardar mucho más; conviene hacerlo de a uno o dos.
